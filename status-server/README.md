# MelTun Status

Публичная страница `https://status.meltun.org` на главном сервере. Python 3.12,
SQLite, один контейнер `meltun-status`, отдельный Compose-проект. Интерфейс
минимальный: текущий статус, история за 3/6/12 часов и 7/30/90 дней, процент
доступности и автоматически открываемые/закрываемые инциденты. Публичные имена —
только страны, повторы получают `#2`, `#3` по порядку списка панели. Флаги —
локальный SVG, без сторонних запросов. Светлая/тёмная тема следует системе,
ручной выбор сохраняется в браузере. Публичный интерфейс не показывает latency,
названия провайдеров, теги нод или сведения о внутренней реализации проверок.
Нажатие на название страны открывает подробности: текущий период без сбоев,
последний сбой и его длительность, число сбоев/недоступность за выбранное окно,
историю и связанные плановые работы. Без наблюдений цифры не придумываются.

## Плановые работы и управление

`https://status.meltun.org/admin` — закрытая страница управления расписанием.
Можно создать или изменить объявление, выбрать все серверы либо конкретные
страны, задать начало/окончание и описание. Все даты вводятся по Москве.
Статусы `scheduled`, `active`, `completed` переключаются по времени автоматически;
публичная страница обновляется раз в 30 секунд. Будущие работы можно отменить
(запись остаётся в управлении), текущие — завершить досрочно с сохранением истории.
Одновременное редактирование защищено номером версии записи.

В период работ страна отмечается синим; в истории фактические сбои сохраняют
свои красные/жёлтые доли с отдельной синей отметкой. Запланированный простой **не вычитается** из расчёта
аптайма. Окончание объявления не означает успешное восстановление сервера:
после него снова показывается фактически измеренное состояние.

Пароль управления отдельный, не `SECRET_KEY` ноды и не токен панели.
На сервере первоначальные данные входа находятся в `/root/meltun-status-admin.txt`
(0600); прочитать их можно из собственной root SSH-сессии. Пароль не публикуется
и не входит в образ или Git. Конфигурация PBKDF2-SHA256 хранится в
`private/status-admin.json`: `salt` (hex), `iterations` (600000), `hash` (hex).
Файл монтируется read-only в `/run/secrets/status-admin.json`; его нужно создать
до запуска Compose. Случайный пароль генерируется на сервере. Сессия — 12 часов,
HttpOnly/Secure/SameSite=Strict; после перезапуска сервиса нужно войти заново.
Пять неудачных попыток в минуту на IP ограничиваются; записи требуют CSRF-токен
и допустимый Origin. Публичный GET API не содержит данных управления.

## Проверки и история

Каждые 60 секунд сервис получает включённые ноды Remnawave и проверяет их
управляющий TCP-порт. Подключение к панели и TCP должны быть исправны для
статуса «Работает». После подключения агента учитывается состояние Xray;
частичный сбой или недоступность подтверждаются двумя последовательными
неудачными проверками. Для самостоятельных записей агента отсутствие пакетов
больше трёх минут означает недоступность. Недоступность панели даёт неизвестное
состояние, кроме нод с актуальным подписанным пакетом.

Аптайм — время в состоянии `up`, делённое на измеренное время (`up`, `down`,
`degraded`). Промежутки без наблюдений не засчитываются как успешные проверки.
Один результат действителен максимум 150 секунд. История до первого наблюдения
пуста; проценты за 90 дней не означают, что наблюдение длилось все 90 дней.
Дневные интервалы и отображаемое время — Europe/Moscow. Часовые периоды —
скользящие окна до текущего момента; шаг 5 минут для 3/6 часов и 10 минут для
12 часов. Процент считается по пересечению реальных интервалов с окном.
Каждый столбик состоит из пропорциональных долей измеренного времени:
зелёная — `up`, жёлтая — `degraded`, красная — `down`. Двухминутный сбой
не закрашивает весь день красным. Это доли, а не хронологический порядок
событий внутри столбика; точная длительность доступна при нажатии/наведении.
Время без наблюдений не добавляется в зелёную долю; полностью пустой столбик серый.
Смежные интервалы
одного состояния объединяются в SQLite. Реальный клиентский VLESS-туннель
этот сервис не проверяет; TCP latency относится к пути с главного сервера.

## Авторизация агента существующим SECRET_KEY

Агент Node Forge декодирует `nodeCertPem` и `nodeKeyPem` из Remnawave
`SECRET_KEY`, проверяет соответствие пары и подписывает канонический JSON
ECDSA/RSA SHA-256. В запросе `POST /api/agent/heartbeat` передаются только
подписанные данные, публичный сертификат и подпись. Приватный ключ/секрет
не передаётся. Центральный сервис проверяет цепочку сертификата только
по локально закреплённому CA панели, подпись, время (±120 секунд) и nonce.
Повторы nonce хранятся в SQLite. CA из входящих запросов не принимается.

Если исходящий IP совпадает с нодой панели, агент дополняет её статус.
Иначе корректный сертификат этой панели позволяет автоматически создать
запись агента. В дальнейшем нода с тем же IP в панели подхватит её историю.
Ключ сертификата привязан к идентификатору агента; смена сертификата разрешена
с известного IP той же ноды. Пакеты без ключа вашей панели не создают записи.
Обновление статуса через интерфейс: вкладка **Статус** в Node Forge.

## Развёртывание на главном сервере

Исходники: `/opt/meltun-status`. Контейнер опубликован только на
`127.0.0.1:3210`; наружу его выдаёт существующий `remnawave-nginx`.
Сети Compose: внешние `meltun_web_meltun_net` и `remnawave-network`.
Данные: named volume `meltun-status_status-data`, файл `/data/status.sqlite3`.
Контейнер работает без root, с read-only filesystem, 160 MiB RAM и 0,5 CPU.

В защищённом каталоге `/opt/meltun-status/private` с правами `0700` находятся
API-токен панели и закреплённый публичный CA. Они не входят в репозиторий или
образ. Файлы монтируются read-only. CA получен из ответа `/api/keygen` панели;
остальные поля ответа не сохраняются. API-токен нужен для чтения списка нод.

```bash
cd /opt/meltun-status
docker compose -f compose.yml up -d --build
curl -fsS http://127.0.0.1:3210/healthz
```

`GET /api/status?days=7|30|90` или `?hours=3|6|12` — только публичные данные.
Одновременное указание days и hours не принимается. IP, управляющие порты,
ключи и внутренние поля агентов в ответ не попадают. Страница `/admin` управляет
только объявлениями о работах, а не Remnawave/SSH. Открытого метода добавления
сервера без подписи нет.

Nginx-блок ограничен маркерами `BEGIN/END MELTUN STATUS` в
`/opt/remnawave/nginx/nginx.conf`. Сертификат находится в существующем
Certbot-каталоге `/root/meltun_web/data/certbot/conf/live/status.meltun.org`.
`meltun-status-certbot.timer` проверяет его дважды в сутки и делает graceful
reload Nginx. Другие сервисы не перезапускаются.

## Проверки и резервная копия

На Linux, где установлены Python 3 и OpenSSL:

```bash
python3 -B -m unittest discover -s tests -q
python3 -B -m unittest discover -s status-server/tests -q
bash -n install-remnanode-manager.sh
node --check status-server/static/app.js
node --check status-server/static/admin.js
node status-server/tests/test_history.cjs
```

Команды запускаются из корня репозитория Node Forge. Серверные тесты проверяют
неизвестные интервалы, настоящий процент, подтверждение/закрытие инцидента,
объединение нод, повторы, подпись, чужой CA и несовпадающий ключ; подробности,
пересечения работ, сохранение реального аптайма, версии, отмену/завершение,
сессии и HTTP-защиту управления. Тестовые объявления создаются только в
временной SQLite, не в production.

Перед обновлением кода сохраняйте `/opt/meltun-status` без публикации `private`,
Nginx-конфиг и согласованную SQLite-копию через `sqlite3.Connection.backup()`.
Не копируйте только основной SQLite-файл при активном WAL. Начальные бэкапы:
`/root/backups/meltun-status-20261018T175501Z` и
`/root/backups/meltun-status-20261018T175608Z`. Для отката верните только блок
статус-сайта из backup, проверьте `nginx -t`, выполните reload и остановите
только `meltun-status`. Named volume и историю сохраняйте.
